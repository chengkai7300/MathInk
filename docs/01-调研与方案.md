# 手写数学公式 → TeX：本地化方案调研与设计

> 版本 v0.1 · 2026-11-16 · 阶段：方案评审（无代码）
> 结论基于公开论文、官方仓库与模型卡；标注「估算」的数字需在 P0 阶段实测。

---

## 0. 结论先行

1. **这件事现在可以全本地做，而且精度比两年前高一个档次。** 当前最强的开源路线不是专用小模型，而是「微调过的 2B–3B 视觉语言模型（VLM）」：Uni-MuMER 用 Qwen2.5-VL-3B 全参微调，在 CROHME 2019 上 ExpRate **79.82%**、HME100K **69.50%**、MathWriting **53.03%**，已超过所有公开的专用 HMER 模型。权重与代码均为 Apache-2.0。
2. **公开基准 ≠ 你的真实数据。** 拍照手写、纸面噪声、中文混排会明显掉点。第一笔投入应该花在「内部评测集 + 纠错闭环」，而不是急着训模型。
3. **推荐架构**：统一图像输入 →（可选）轻量快速通道 → 3B VLM 主识别 → LaTeX 归一化/校验/渲染比对 → 候选与人工纠错。整页笔记再叠加版面与公式检测。
4. **许可比精度更危险。** CROHME 数据仅限研究、PosFormer 权重仅限学术、MathWriting 是 CC BY-NC-SA。若产品要商用，必须用「Apache/MIT 基座 + 自采/合成数据」重训，不能直接拿论文权重上线。
5. **三档配置**：轻量（纯 CPU/浏览器，CoMER INT8 仅 7.2 MB）、标准（3B VLM，8 GB 显存起）、整页（PaddleOCR-VL 0.9B + 检测）。建议先做标准档 MVP。

## 1. 需求边界（当前假设，待你确认）

| 维度 | 当前假设 | 对方案的影响 |
| --- | --- | --- |
| 输入形态 | 拍照/扫描为主，画布手写为辅；两者统一转成图像 | 只需一套图像模型；画布只做渲染，不传笔迹 |
| 公式数量 | MVP：一张图一个公式；二期：整页笔记 | 决定要不要公式检测/版面模型 |
| 终端 | Windows 10/11 桌面，本地服务 + 浏览器界面 | 打包方式、模型分发、GPU 探测 |
| 网络 | 默认离线，不依赖云 API | 模型必须能本地加载；首次下载可接受 |
| 输出 | LaTeX（KaTeX/MathJax 兼容），可选 MathML | 后处理与校验规则 |
| 内容范围 | 纯数学公式；中文/英文混排二期 | 是否需要 PaddleOCR-VL 一类文档模型 |
| 商业属性 | 未定（按「可能商用」设计） | 直接决定数据集与权重选择 |
| 性能目标 | GPU 单公式 ≤2 s，CPU ≤8 s；「无需修改即可用」≥80% | 模型档位与是否加快速通道 |

> 如果你的真实场景是「边写边识别」（类似 Apple Math Notes），延迟要求会变成 <300 ms，方案要改为在线笔迹模型，见 §6.7。

## 2. 为什么这件事不简单

- **二维结构**：上下标、分式、根号、求和上下限、矩阵、多行对齐，输出是带嵌套的 LaTeX 序列，不是从左到右的字符串。
- **符号歧义**：`z/2`、`1/l`、`x/×`、`o/0`、`\alpha/a`，以及手写连笔导致的粘连。
- **书写风格**：同一个人不同时间写得都不一样，遑论不同人。
- **真实场景噪声**：纸张纹理、阴影、透视、笔迹偏淡、格子线干扰、拍照角度。
- **长表达式与深嵌套**：MNE-N3（三层嵌套）上最好的模型也只有 **46.72%**，这是当前的能力边界。
- **评测口径不统一**：ExpRate 是严格字符串匹配，语法等价的写法会被判错；CDM/ExpRate@CDM 是渲染后视觉比对，更接近用户感受。
- **数据许可**：这是最容易在立项时被忽略、在上线前爆雷的一项。

一个常见误区：直接拿 pix2tex / Pix2Text / PP-FormulaNet 当手写识别用。它们的主训练集是**印刷体公式**，手写域偏移明显；PaddleOCR 文档虽声称 PP-FormulaNet-L 适用手写场景，但没有公开的手写基准数字，不能当作保证。

## 3. 技术路线全景

### 3.1 专用 HMER 小模型（encoder-decoder）

代表：WAP → DWAP → CAN → BTTR → CoMER → PosFormer → TAMER → SSAN，参数通常 6–30 M，输入单行公式图，输出 LaTeX 序列。

- **优点**：极小（CoMER INT8 仅 7.2 MB）、CPU 甚至浏览器可跑、易导出 ONNX、延迟低。
- **缺点**：在 CROHME 这类「干净单行」数据上训练，真实拍照掉点大；长表达式和深嵌套弱；换场景必须重训。
- **精度**（CROHME ExpRate，%）：

| 模型 | CROHME14 | CROHME16 | CROHME19 | 备注 |
| --- | --- | --- | --- | --- |
| BTTR | 53.96 | 52.31 | 52.96 | Transformer + 双向解码 |
| ABM | 56.85 | 52.92 | 53.96 | 双向互学习 |
| CoMER | 59.33 | 59.81 | ≈56.2 | 覆盖率注意力 |
| PosFormer | 62.68 | — | 64.97 | 位置森林，ECCV 2024 |
| IMPO（PosFormer + 图像级奖励） | 63.89 | — | 66.34 | CVPR 2026 |

> PosFormer 的代码与权重明确「仅限学术研究」，商用不可用；CoMER 仓库未声明许可证，需谨慎。

### 3.2 文档级公式 OCR（印刷体为主）

代表：pix2tex（LaTeX-OCR）、Pix2Text MFR、PaddleOCR PP-FormulaNet 系列、UniMERNet、TexTeller。

- 生态成熟、部署简单（ONNX/Paddle）、印刷体精度高。
- **手写不是它们的强项**；UniMERNet 训练集包含手写/扫描样本，相对好一些；Pix2Text 的付费 MFR 模型据称专门优化过手写。
- 精度/体积（PaddleOCR 官方数据，印刷体测试集）：

| 模型 | En-BLEU | 体积 | CPU 延迟（常规模式） | 许可 |
| --- | --- | --- | --- | --- |
| PP-FormulaNet-S | 87.00 | 224 MB | 254 ms | Apache-2.0 |
| PP-FormulaNet-L | 90.36 | 695 MB | 3131 ms | Apache-2.0 |
| PP-FormulaNet_plus-M | 91.45 | 592 MB | 1616 ms | Apache-2.0 |
| UniMERNet | 85.91 | 1530 MB | 8288 ms | 见仓库 |
| pix2tex | —（印刷体） | ~50 MB | CPU 可跑 | MIT |
| Pix2Text MFR | —（印刷体，付费版优化手写） | 小 | CPU 可跑 | MIT（付费模型另购） |

### 3.3 通用 VLM 微调（当前 SOTA）

思路：不改造网络，直接把「公式图 → LaTeX」当成图文指令任务，用 HMER 数据全参微调 2B–3B 的 VLM。

代表：**Uni-MuMER**（NeurIPS 2025 Spotlight，北大），基座 Qwen2.5-VL-3B，加入 Tree-CoT（语法树思维链）、Error-Driven Learning（错误驱动学习）、Symbol Counting（符号计数）三个辅助任务。

**零样本 vs 微调（CROHME ExpRate，%）**：

| 模型 | CROHME14 | CROHME16 | CROHME19 | 平均 |
| --- | --- | --- | --- | --- |
| GPT-4o | 50.61 | 46.03 | 49.79 | 48.81 |
| Gemini 2.5-flash | 58.01 | 52.74 | 55.21 | 55.32 |
| Qwen2.5-VL-3B | 38.64 | 37.75 | 37.45 | 37.95 |
| Qwen2.5-VL-7B | 55.98 | 50.92 | 49.62 | 52.17 |
| **Uni-MuMER-3B（微调）** | **82.25** | **78.29** | **79.82** | **≈80.1** |

**跨数据集表现（Uni-MuMER-3B，ExpRate）**：

| 数据集 | 样本数 | ExpRate |
| --- | --- | --- |
| CROHME 2023 Test | 2,300 | 69.52% |
| HME100K Test（真实拍照） | 24,607 | 69.50% |
| MathWriting Test（渲染离线） | 7,643 | 53.03% |
| MNE-N1 / N2 / N3（嵌套） | 1875 / 304 / 1464 | 75.89 / 57.89 / 46.72 |

家族里还有更小的变体：Qwen3.5-2B（平均 73.09%）、Qwen3-VL-2B（72.49%）、Qwen3-VL-4B（71.60%）。**2B 级已经够用**，对显存和延迟更友好。

- **优点**：复杂结构、长表达式、真实场景综合最强；天然支持多行、矩阵；prompt 可扩展（如「只输出 LaTeX」）。
- **缺点**：2–8 GB 权重，CPU 上慢；存在「幻觉」——可能补出图上没有的符号；需要 GPU 才有好体验。
- **许可**：代码与权重 Apache-2.0；但训练数据包含 CROHME / MathWriting / HME100K，**数据许可会传导**（见 §9.1）。

### 3.4 文档 VLM（面向整页）

代表：**PaddleOCR-VL 0.9B**（Apache-2.0，2026-11 仍在更新）、dots.ocr 1.7B、MonkeyOCR 3B、MinerU2.5。

- 0.96B 参数、2.1 GB，OmniDocBench 公式 CDM 91.43，官方宣称支持手写公式与中英混排。
- 适合「整页笔记 / PDF / 试卷」的元素级解析；对孤立公式的低延迟场景偏重。
- 如果最终产品要处理「中文 + 公式混排的整页笔记」，这是比通用 VLM 更省算力的选择。

### 3.5 商业方案（仅作精度参照，不推荐本地化选型）

| 方案 | 形态 | 备注 |
| --- | --- | --- |
| Mathpix | 云 API | 手写与复杂排版最强，按量计费，数据出本机 |
| SimpleTex | 云 API | 国内产品，免费额度多，精度接近 Mathpix |
| MyScript | 端侧 SDK | 手写数学的老牌方案（Apple Math Notes 同类技术），授权费高 |

结论：若要「本地 + 可控成本」，商业 API 只能当精度上限参照。

## 5. 关键基准与口径说明

1. **ExpRate**：整条 LaTeX 完全匹配才算对，最严格；公开论文主要报这个。
2. **ExpRate@CDM / CDM**：把预测与真值都渲染成图，用字符检测比对，能容忍语法等价写法，更接近「用户看着一样」。
3. **CER / EM**：MathWriting 用 token 级 CER 与 Exact Match，和 ExpRate 不完全可比。
4. **不要跨口径比较**：MathWriting 上「在线笔迹 CTC 模型 EM 60%」和「离线 VLM ExpRate 53%」不是同一指标，不能直接得出谁更强。

**MathWriting 官方基线**（在线笔迹，测试集）：CTC Transformer 35 M，CER **5.49**、EM **60**；PaLI 700 M，CER 5.95、EM 64；PaLIGemma 3B，CER 5.97、EM 69；Google OCR（离线），CER 7.17、EM 53。说明「有笔迹时序」比「只有图」天然占优——这也是画布场景可以做得更好的原因。

## 6. 推荐方案

### 6.1 总体架构

```
┌─────────────┐   图片/画布    ┌──────────────┐   crop+预处理   ┌─────────────────┐
│  Web 前端    │ ────────────▶ │  FastAPI 服务 │ ─────────────▶ │  推理引擎         │
│  (React)     │               │  /v1/recognize│                │  VLM / ONNX      │
└─────────────┘ ◀──────────── └──────────────┘ ◀───────────── └─────────────────┘
       │            LaTeX+置信度        │
       │                               ▼
       │                     ┌──────────────────┐
       └─────────────────── │ LaTeX 后处理与校验 │
                             │ 归一化/修复/渲染比对│
                             └──────────────────┘
```

### 6.2 主链路（MVP 必做）

1. 输入：上传/拍照/画布渲染，统一转 PNG（长边 1024–1536，灰度或保留彩色）。
2. 预处理：自动裁掉空白边、按笔迹外接框外扩 5–8%、轻微去倾斜、对比度拉伸；不做重二值化（会伤浅笔迹）。
3. 主模型：**Uni-MuMER-3B**（或 Qwen3-VL-2B 变体），prompt 固定为「输出该手写公式的 LaTeX，不要解释」。
4. 后处理：归一化 → 语法校验 → 必要时自动修复 → 渲染比对 → 置信度。
5. 交互：展示渲染结果 + 可编辑 LaTeX + 候选（可选）+ 「重新识别选中区域」。

### 6.3 快速通道（可选，二期）

- **CoMER INT8 ONNX**（encoder 3.4 MB + decoder 4.0 MB）在浏览器/CPU 内运行，用于画布上的「边写边看」预览。
- 只做预览，最终结果仍由主模型确认；避免小模型把用户带偏。
- 若不做实时预览，MVP 可以完全跳过这一层，架构更简单。

### 6.4 整页模式（二期）

- 版面/公式检测：Pix2Text MFD（MIT）或 PP-DocLayout。
- 公式逐块送主模型；正文中文交给 RapidOCR/PaddleOCR。
- 或直接用 **PaddleOCR-VL 0.9B** 一把梭，输出 Markdown + LaTeX，适合「整页笔记数字化」。
- 注意：矩阵/多行公式容易被检测器拆成多个框，需要在后处理里做框合并（按水平/垂直间距与 IoU）。

### 6.5 不建议的做法

- ❌ 从零训练 HMER 模型（数据、算力、调参成本远高于微调）。
- ❌ 直接分发 PosFormer 权重（仅学术许可）。
- ❌ 用 CROHME 训练出的权重做商业产品（数据许可仅限研究）。
- ❌ 只上 pix2tex/Pix2Text 就宣称支持手写（域偏移，体验会崩）。
- ❌ 追求 100% 准确率：公开 SOTA 也只有 80% 左右，产品必须靠纠错 UI 兜底。

### 6.6 三档配置

| 档位 | 硬件 | 模型 | 单公式延迟 | 预期 ExpRate | 适用 |
| --- | --- | --- | --- | --- | --- |
| 轻量 | 无独显 / 8 GB RAM | CoMER INT8 | 0.2–0.6 s | ≈56% | 浏览器插件、低配机 |
| 标准 | RTX 3060 12G（bf16/int4）或 4060 8G（int4） | Uni-MuMER-3B | 1–3 s | ≈80% | 桌面主推 |
| 整页 | RTX 4060Ti 16G+ | PaddleOCR-VL 0.9B + 检测 | 2–5 s/页 | 公式 CDM 91（官方） | 笔记/试卷数字化 |

### 6.7 如果目标是「边写边识别」

在线笔迹（含时序）比离线图像更准，但开源成熟度低：MathWriting 只给了基线模型与数据，没有开箱可用的产品级在线识别器。务实做法：

1. 画布采集笔迹 → 渲染成图 → 主模型（延迟 1–3 s，可接受）；
2. 若必须 <300 ms，用 CoMER INT8 做草稿识别，停笔 500 ms 后再用主模型校正；
3. 长期再考虑自训在线 CTC/Transformer（需要 MathWriting 或自采笔迹数据，注意许可）。

### 6.8 与现成开源项目的关系

- **LocalMathOCR**（MIT）：已经做了「FastAPI + React + 画布 + Pix2Text/pix2tex/UniMERNet 切换 + 编辑导出」的完整壳子，但它的「手写」只是把画布渲染成图后交给印刷体模型，真实手写精度有限。
- **handwritten-ocr**（MIT）：做了「整页手写中文 + 公式 → Markdown」的检测+识别流水线（Pix2Text MFD + RapidOCR + UniMERNet），适合整页场景，公式精度受 UniMERNet 限制。
- **本方案的增量**：用 HMER 专用微调 VLM 替代印刷体模型解决手写精度；把「归一化/校验/渲染比对/置信度/纠错回流」做成独立层；按「单公式 → 整页」分阶段交付。壳子层可以直接借鉴上述两个项目，不必重造。

## 7. 系统设计（只定模块与接口，不写实现）

### 7.1 模块划分

| 模块 | 职责 | 技术选型建议 |
| --- | --- | --- |
| `apps/web` | 上传/画布/裁剪/结果/编辑/导出 | React + Vite + Konva + KaTeX + MathLive |
| `services/api` | 编排、鉴权（本地可省）、任务队列 | FastAPI + Uvicorn |
| `services/infer` | 模型加载与推理 | vLLM（GPU）/ llama.cpp（CPU/int4）/ ONNX Runtime |
| `packages/latex` | 归一化、校验、修复、渲染 | Python: pylatexenc + latex2sympy；前端: KaTeX |
| `data/` | 评测集、合成管线、标注 | 脚本 + 版本化清单（DVC 可选） |
| `deploy/` | 安装包/Docker | Tauri 或 Electron + 打包脚本 |

### 7.2 API 草案

| 方法 | 路径 | 入参 | 出参 |
| --- | --- | --- | --- |
| POST | `/v1/recognize` | `image`(file/base64)、`mode`(auto/fast/accurate)、`hint` | `latex`、`latex_display`、`confidence`、`alternatives[]`、`timing` |
| POST | `/v1/verify` | `latex` | `valid`、`errors[]`、`rendered_png` |
| POST | `/v1/detect` | `image` | `boxes[]`（整页模式） |
| POST | `/v1/batch` | 多图 | 任务列表 |
| GET | `/v1/health` | — | 模型状态、设备、显存 |

### 7.3 前端交互要点

- 画布：Pointer Events 采集，支持压感（可选）、撤销、橡皮擦、清空；导出时按 2× 渲染，避免细笔画丢失。
- 上传：拖拽/粘贴/拍照；进入裁剪模式，允许框选单个公式。
- 结果区：左侧原图、右侧渲染公式；下方 LaTeX 源码（可编辑，实时 KaTeX 预览）。
- 候选：展示 2–3 个备选（来自多次采样或 beam），点击替换。
- 低置信度高亮：按 token 概率给源码染色（差异化功能，见 §8.4）。
- 导出：复制 LaTeX、复制 `$...$`、Markdown、PNG/SVG；二期 Word/PDF。

### 7.4 部署与隐私

- 默认「本地服务 + 本机浏览器」，模型文件随安装包分发或首次运行下载（带 SHA256 校验）。
- 全流程不出网；日志不含图片内容（或仅本地）。
- Windows 安装包建议 Tauri（体积小）或 Electron（生态成熟）；同时提供 Docker 供内网服务器部署。

## 8. TeX 后处理与质量闭环（这是产品的差异化）

### 8.1 归一化规则（草案）

1. 去掉 `\left` / `\right` / `\displaystyle` / `\limits` / `\!` 等排版修饰。
2. `\dfrac`、`\tfrac` → `\frac`；`\over` → `\frac`。
3. 单字符上下标补花括号：`x^2` → `x^{2}`。
4. 统一空格与换行，去掉首尾空白与多余 `\\`。
5. 全角符号转半角（`＋`、`（`、`，`）。
6. 保留语义：`\cdot` 与 `\times` 不互换；`\text{}` 内的中文保留。
7. 输出两种形态：`latex`（无定界符，供编辑）与 `latex_display`（`\[...\]`，供插入）。
8. 多行输出统一为 `\begin{aligned}...\end{aligned}`。
9. 保留 `\begin{bmatrix}` 等环境，不做矩阵扁平化。
10. 记录 `raw` 原始输出，便于回归对比。

### 8.2 语法校验与自动修复

- 括号/花括号配平；`\frac`、`\sqrt` 参数个数检查。
- 用 `pylatexenc` 解析 + KaTeX 渲染双校验；KaTeX 失败则判为无效。
- 常见修复：补 `}`、补 `\right`、把 `^` 后多字符包进 `{}`、把 `\begin{matrix}` 补全 `\end`。
- 修复失败 → 返回低置信度 + 原文，交给用户。

### 8.3 渲染比对（强烈建议）

把预测 LaTeX 渲染成图，与原图做结构比对（SSIM、或 CDM 的字符检测匹配）。它能抓住「符号对但结构错」这类文本指标看不出的问题，也是 IMPO（CVPR 2026）用图像级奖励提升 HMER 的核心思路。工程上不必训练奖励模型，规则化比对即可作为置信度信号。

### 8.4 置信度

- VLM：取生成 token 的平均对数概率（vLLM 支持 logprobs）；或采样 3 次做一致性投票。
- 小模型：decoder 序列概率。
- 融合：`score = w1 * 模型置信度 + w2 * 渲染比对分 - w3 * 结构风险惩罚`。
- 展示：>0.9 绿、0.7–0.9 黄、<0.7 红并默认展开候选。

### 8.5 纠错回流（数据飞轮）

- 用户每次「修改后采纳」都记录 `(图片, 模型输出, 用户最终 LaTeX)`。
- 本地默认不上传；提供「贡献样本」开关，脱敏后进入训练集。
- 每月用新样本做一次 LoRA 增量微调，形成闭环。

**结论**：如果确定商用，训练数据应走「自采 + 合成 + Apache/MIT 许可的公开印刷数据」，把 CROHME 只用于离线评测（评测本身也建议法务确认）。这会牺牲一点起步精度，但避免上线后的许可风险。

### 9.2 合成数据管线

1. LaTeX 语料：arXiv 摘要/公式、Wikipedia 公式、教材题库（注意来源许可）。
2. 渲染：KaTeX/MathJax → 高分辨率 PNG；多字体（Latin Modern、Asana、STIX）。
3. 手写化：两条路
   - **符号拼接**（MathWriting 做法）：用真实手写单符号库按 LaTeX 布局拼装，再整体做形变；
   - **风格迁移**：印刷图 → CycleGAN/扩散模型转手写风格（成本高，需调）。
4. 增强：透视、旋转 ±5°、弹性形变、笔画粗细、墨色（蓝/黑）、纸纹、阴影、模糊、JPEG 噪声。
5. 过滤：渲染比对筛掉「图与 LaTeX 不一致」的样本。
6. 规模：50–100 万对起步；长表达式单独加权。

### 9.3 自采数据

- 目标：覆盖真实设备与纸张（手机拍照、平板、白纸、网格纸、横线纸）。
- 规模：MVP 阶段 1,000–3,000 张即可做 LoRA；上线后靠纠错回流扩到 1–3 万。
- 标注：内部 Web 标注工具（画框 + 输入 LaTeX + 渲染校验），双人抽检 10%。
- 合规：签署知情同意，去除个人信息。

### 9.4 微调方案

| 方案 | 成本 | 适用 |
| --- | --- | --- |
| LoRA（r=16–32） | 1×A100 40G 或 4090 24G，1–2 天 | 首选，快速迭代 |
| 全参微调 | 8×A100 80G，约 1 天（Uni-MuMER 配置） | 精度不够时 |
| 蒸馏到 2B/1B | 中 | 追求 CPU/端侧 |

- 基座：Qwen3-VL-2B / Qwen2.5-VL-3B（Apache-2.0）。
- 目标格式：直接输出归一化 LaTeX；可选加 Symbol Counting（便宜且有效），Tree-CoT/EDL 复杂度高，二期再评估。
- 训练数据配比建议：合成 60%、自采 30%、公开印刷 10%；按表达式长度分桶采样。

### 9.5 成本估算（估算）

- 合成 50 万张：单机 GPU 渲染 + 增强，约 1–2 天。
- LoRA 微调：租 1×A100 约 ¥10–20/小时 × 24–48 h ≈ ¥300–1,000。
- 全参微调：8×A100 约 ¥100–200/小时 × 24 h ≈ ¥2,400–4,800。
- 推理：本地零边际成本；若做云服务，3B int4 单卡可支撑个位数并发。

## 附录 B：术语

- **HMER**：Handwritten Mathematical Expression Recognition，手写数学公式识别。
- **ExpRate**：整式完全匹配率。
- **CDM**：Character Detection Matching，渲染后字符检测比对，用于视觉等价评测。
- **SymLG**：Symbol Layout Graph，CROHME 的符号布局图真值格式。

- **Tree-CoT**：把公式语法树作为思维链中间表示，再输出 LaTeX。
