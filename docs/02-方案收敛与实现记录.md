## 1. 锁定后的约束

| 维度 | 决定 | 影响 |
| --- | --- | --- |
| 显卡 | RTX 4070 Ti，12 GB 显存 | 2B VLM 可跑（Q4 约 1.5–2 GB），3B bf16 也可但余量小 |
| 输入 | **鼠标在画布上手写** | 笔画干净但抖动、尺度不可控；必须控制内容尺寸 |
| 公式数量 | 单张单公式 | 不需要版面/公式检测 |
| 终端 | 本地服务 + 浏览器界面 | FastAPI + 静态前端，无需 Electron |
| 模型 | 本地，提供下载选项 | CoMER 7.2 MB + VLM 1.5 GB，放 `models/` |
| 输出 | LaTeX，纯数学 | 无需中文混排、无需 Word |
| 商业属性 | **非商用** | CROHME 数据与学术权重可用（仅限自用/研究） |
| 性能 | 单个公式 **< 1 s** | VLM 实测 61–120 ms，CoMER 兜底 100–360 ms |

## 2. 决策：默认引擎用 CoMER INT8

| 候选 | 结论 | 原因 |
| --- | --- | --- |
| **Uni-MuMER 2B（Q4 GGUF，1.5 GB）** | **默认** | 短公式 81.3%、全量 72.3%，GPU 上 61–120 ms；同机比 CoMER 更快且更准 |
| **CoMER INT8（7.2 MB）** | **兜底 / 极速** | 无 GPU 可用，CPU 100–360 ms；词表只有 113 token |
| PosFormer | 不用 | 精度不如 VLM，推理链路重，学术许可 |
| Qwen2.5-VL-3B 零样本 | 不用 | 38%，远低于微调版 |
| pix2tex / PP-FormulaNet | 不用 | 印刷体训练，手写掉点严重 |
| 云端 Mathpix | 不用 | 违背本地化目标 |

**关键反转**：原计划「CoMER 主打、VLM 二期」被实测推翻。2B VLM 在 4070 Ti 上
Q4 量化后单张只要 **61–120 ms**，比 CPU 上的 CoMER 还快，精度高 8–14 个点。
因此默认引擎改为 VLM，CoMER 退居 CPU 兜底。

## 3. 实测数据

### 3.1 CROHME 2019 评测

| 子集 | 预处理 | ExpRate | ≤1 编辑 | CER | p50 | p95 |
| --- | --- | --- | --- | --- | --- | --- |
| 400 张等距抽样 | 官方 | **58.0%** | — | 11.1% | 537 ms | 1447 ms |
| 150 张抽样（长公式占 55%） | 官方 | 47.3% | 61.3% | 16.2% | 626 ms | 1221 ms |
| 前 100 张 | 官方 | 76.0% | — | 14.5% | 83 ms | 124 ms |
| 前 100 张 | 裁切 + 官方缩放（画布近似） | 74.0% | — | 16.2% | 78 ms | 139 ms |
| 前 100 张 | ink-on 的「缩放到 128 高」 | 37.0% | — | 69.6% | 142 ms | 251 ms |

**重要**：CROHME 2019 里长公式占比很高，抽样方式会让整体数字在 **47%–58%** 之间波动；
前 100 张的 76% 是短公式偏多的偏差样本，**不能当作整体精度**。
400 张的 58.0% 与 CoMER 论文的 56.2% 基本一致，说明复现正确。按长度拆解见 3.4。

**延迟说明**：p50 537 ms 包含大量 800–1024 px 宽的公式；鼠标画布常见宽度 200–600 px，
实测 105–360 ms（见 3.2），仍在 1 s 内。p95 1.4 s 属于极端宽/长样本。

### 3.2 画布实测

| 内容尺寸 | 端到端 | 说明 |
| --- | --- | --- |
| 211 × 65（`x+1`） | 105 ms | 典型短公式 |
| 360 × 200 | 109 ms | 高度大但宽度小 |
| 700 × 70 | 360 ms | 宽度是主要成本 |

空载时 HTTP 往返约 10 ms；编码占 80–90%，解码 6–60 ms。
结论：**<1 s 目标对典型鼠标输入轻松达成**，不需要 GPU。

### 3.3 beam 搜索的教训

beam=3 在 60 张抽样上跑了 6 分钟仍未完成，单张 5–10 s。原因不是模型大，而是：

- 导出的 decoder 没有 KV cache，每一步都要重算整段前缀；
- beam 把每步的解码次数再乘 3；
- 宽公式的 encoder 特征又多，attention 成本随宽度上升。

**结论**：默认贪心（beam=1）。beam 只适合离线批量，且要先解决 KV cache，不能放进 <1 s 的交互路径。

### 3.4 按公式长度拆解（同一批 150 张，steps=20）

| 真值 token 数 | 样本 | ExpRate | ≤1 次编辑 | 说明 |
| --- | --- | --- | --- | --- |
| 1–5（全量） | **209** | **73.7%** | **91.4%** | 产品主场景，p50 224 ms |
| 1–5（抽样） | 31 | 77.4% | 100% | 与全量一致 |
| 6–10 | 29 | 69.0% | 82.8% | |
| 11–15 | 23 | 56.5% | 87.0% | |
| 16–25 | 39 | 35.9% | 43.6% | |
| 26+ | 28 | 0% | 0% | 被 20 步上限截断，也是能力外 |

典型错误（短公式）：

```
x ≥ c        → x ≥ C         大小写歧义
G × G        → G × 6         6/G 形近
sin α = 0    → sin a = 0     \alpha / a
√{-g}        → √{-8}         8/g 形近
-0.999       → -0,999        小数点/逗号
```

这些**不是结构错误**，而是符号级视觉歧义；用户点一下就能改。真正难的是长公式与深嵌套。

**产品含义**：把「单行、≤10 个符号」作为主场景。短公式全量 209 张：74% 完全正确、
91% 只需 ≤1 次修改；中等公式 69%；长公式引导用户用二期 VLM 或拆行输入。

### 3.5 VLM 接入结果（Uni-MuMER 2B Q4，llama.cpp Vulkan）

| 子集 | n | ExpRate | ≤1 编辑 | CER | p50 | p95 |
| --- | --- | --- | --- | --- | --- | --- |
| ≤5 符号（全量） | 209 | **81.3%** | **93.3%** | 9.7% | **61 ms** | 84 ms |
| 400 张等距抽样（全长度） | 400 | **72.3%** | 86.0% | 5.8% | **120 ms** | 276 ms |

- 长公式（≥15 token）130/195 全对，明显强于 CoMER。
- 首次请求约 9 s（Vulkan shader / vision graph 编译），已用启动后的后台 warmup 掩盖。
- 输入：CROHME 图需反转为白底黑字；画布直接渲染白底黑字，与训练分布一致。
- 结论：**VLM 在速度与精度上同时优于 CoMER**，默认引擎切换为 VLM。

## 4. 关键发现：预处理必须匹配训练

这是本次最有价值的一条工程经验。

- `ink-on` 的开源实现会把内容**缩放到固定 128 高**，再放进 256 高画布。
- 直接照搬，CROHME19 只有 **37%**；改成 CoMER 官方预处理后是 **76%**，差一倍。
- 官方做法（见 CoMER `datamodule/dataset.py`）：
  1. 灰度、不做二值化、不做 bbox 裁切；
  2. **只有超出范围才缩放**：高 `>256` 或宽 `>1024` 才缩小，高/宽 `<16` 才放大；
  3. 其余保持原始像素尺寸；
  4. 左上角放置，右侧/下方补黑（0），mask 标记 padding；
  5. 画布高固定 256，宽按 64 对齐。

**对画布的启示**：不要为了「填满画布」而放大用户笔迹。鼠标写多大就是多大，接近 CROHME 的
100–200 px 高最稳；写得太小（<40 px）或太大（>256 px）要提示用户。

## 5. 鼠标画布设计

### 5.1 尺寸与坐标系

- 逻辑画布 900 × 360 CSS px，按 `devicePixelRatio` 放大 backing store，保证高清屏不糊。
- 笔宽 3 CSS px；坐标以 CSS px 存储和上传，**不乘 DPR**，保证不同屏幕得到同一张图。
- 显示用二次贝塞尔平滑（中点法），服务端再按 3 px 间距重采样，双端一致。

### 5.2 从笔画到模型输入

```
strokes(CSS px)
  → bbox + 16 px padding
  → 2× 超采样绘制（Pillow，白笔黑底，圆头圆角）
  → 降采样回原尺寸（LANCZOS，抗锯齿）
  → 仅当 h>256 / w>1024 时等比缩小（BILINEAR）
  → 放到 256 高、64 对齐的黑色画布左上角
  → float32 /255 + padding mask
```

### 5.3 为什么上传笔画而不是 PNG

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **上传 strokes（当前）** | 体积小（几 KB）、分辨率无关、可重放、可换渲染参数 | 服务端要复刻绘制逻辑 |
| 上传 PNG | 所见即所得 | 受 DPR/抗锯齿影响，压缩伪影，体积大 |

### 5.4 鼠标输入特有的问题与对策

| 问题 | 影响 | 对策 |
| --- | --- | --- |
| 抖动、采样点密 | 笔画毛刺 | 1.2 px 距离阈值 + 二次贝塞尔 + 3 px 重采样 |
| 写得太小（<40 px） | 放大后模糊、符号粘连 | 页脚实时显示内容尺寸并提示「建议高度 60–250」 |
| 写得太大（>256 px） | 被缩小、笔画变细 | 同上提示；必要时限制画布高度 |
| 一笔画多个符号 | 结构歧义 | 提示「符号之间抬笔」；后续加自动切分 |
| 鼠标离开画布 | 断笔 | pointer capture + `pointerleave` 收尾 |
| 双击/误触 | 空笔画 | `is_meaningful` 过滤（总长 <15 px 或点数 <6 丢弃） |

## 7. 能力边界（必须让用户知道）

**CoMER 词表只有 113 个 token**（CROHME 标准集）：四则、分式、根号、上下标、括号、
`\int \sum \lim \sin/\cos/\tan/\log`、常见希腊字母、`\leq \geq \neq \pm \times \div` 等；
不支持矩阵、偏导 `\partial`、`\nabla`、`\hat/\bar/\vec`、`\mathbf`、多行、中文。

**VLM（默认）** 不受 113 词表限制，能输出更长的 LaTeX，长公式正确率明显更高；
但训练分布仍以 CROHME 风格为主，矩阵/多行/中文混排不在保证范围内。

**产品表述建议**：定位「单行数学公式」；复杂排版建议拆行或人工编辑。

- 路由：`auto`/`vlm` 走 VLM；VLM 不可用时回退 CoMER；UI 可手动切「极速」。

## 11. 双端模式（v0.4）

- **主机端** `/`：只读镜像 + 结果 + 复制 + 历史 + 二维码。
- **平板端** `/pad`：全屏书写、笔压变宽、手掌防误触、撤销/清空/识别、自动识别、全屏。
- **逻辑画布随输入设备视口动态生成**（横屏约 1000×684、竖屏约 630×900），
  平板整块区域可写；旋转时按比例缩放已有笔画。
- **PC 主机端也可直接书写**：鼠标 / 触屏 / 触控笔，与平板共用会话；非可写边距有遮罩提示。
- WebSocket 协议：`hello` / `stroke` / `preview` / `undo` / `clear` / `recognize` /
  `state` / `result` / `peers` / `error`。
- 识别在主机进程内执行，结果广播给两端；pad 只做输入和状态提示。
- 局域网发现：服务端探测本机 IP（优先 192.168/10/172.16-31，排除 198.18、169.254、127），
  主机页生成二维码；可用 `MATHINK_LAN_IP` 覆盖。
- 起服务必须监听 `0.0.0.0`（`start.ps1` 已改），否则平板连不上。
- 安全：无鉴权，仅适合可信局域网；不要做公网端口映射。

## 12. 进程生命周期与托盘（v0.1.2）

**问题**：关闭启动窗口后 `llama-server` 残留，约 1.9 GB 显存不释放。
根因是它只在 FastAPI lifespan 关闭钩子里被停止；窗口关闭/强杀/崩溃时 lifespan 不执行。

**修复**：

- `launcher.py`：托盘程序，uvicorn 跑在同一进程的后台线程，llama-server 是它的子进程。
- **Job Object**（`KILL_ON_JOB_CLOSE`）：子进程在 job 中，主进程死亡时由 Windows 回收。
- 退出路径：`server.should_exit` → join → `vlm_server.stop()` → 扫残留 → `icon.stop()` → `os._exit`。
- 启动路径：单实例互斥锁 → 清理遗留 llama-server → 起服务 → 托盘。
- `stop.ps1` → `launcher.py --stop`（PID 树）→ 端口/进程兜底。
- 占用：llama 上下文 2048、槽位 1；实测 VLM 约 1.9 GB 显存、1.6 GB 内存。
- 托盘菜单含「释放显存」，下次识别按需重载。

## 13. 多设备房间（v0.1.4）

- **目标**：一台 PC 做服务器，局域网内多台 PC/平板同时使用，画布与识别结果同步。
- 服务端 `SessionManager`：`room -> Session`，默认 `main`；WebSocket `?room=team-a` 加入独立房间。
- 每个房间独立维护：笔画、画布尺寸、最后结果、在线 pad/host、`rev` 版本号。
- **rev**：每次笔画/撤销/清空/改画布递增；识别结果携带开始时的 rev，
  客户端忽略 `rev` 小于当前画布版本的结果，避免慢请求覆盖新书写。
- **画布锁定**：房间内第一个 pad 的视口比例决定逻辑画布，之后锁住；
  其他设备按比例适配，多余区域画阴影边距；清空房间后解锁。
- **广播**：笔画、预览、结果、在线数都只在房间内广播；多主机同时显示同一结果。
- **访问**：服务监听 `0.0.0.0`；其他 PC 打开 `http://<服务器IP>:8848/`；
  `scripts/allow_firewall.ps1` 添加 Windows 防火墙入站规则。
- **并发**：房间内识别用 `asyncio.Lock` 串行；VLM 在服务器 GPU 上单实例，
  多设备主要增加显示连接，开销很小。
